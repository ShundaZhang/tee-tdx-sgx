安全模型

容器沙箱与机密 Pod 的区别

容器安全可以指运行隔离、镜像来源验证，或防止基础设施运营者读取工作负载。CoCo 处理第三类问题，把 Pod 放进机密 VM，并在授权秘密前验证 Guest 的初始状态。

模型隔离边界工作负载依赖什么
普通 OCI 容器namespace、cgroup 和内核安全机制工作负载共享 Worker 内核，拥有宿主特权的一方可以读取其状态。
Kata ContainersPod 沙箱拥有独立虚拟机与 Guest 内核虚拟化隔离将工作负载与 Worker 分开。能否抵御拥有特权的宿主，取决于虚拟机使用的技术。
运行于硬件 TEE 上的 CoCo由 Intel TDX 或 AMD SEV-SNP 等平台提供保护的机密 PodVM硬件保护 Guest 私有状态，工作负载所有者依据远程证据和策略授权敏感资源。

工作负载依赖 CPU 与固件、Guest OS、Guest 内运行时、应用以及可信的验证和发放服务。宿主仍能控制调度或中断 VM。共享 I/O、流量元数据和应用日志各自需要保护。写入 Pod YAML、普通 Kubernetes Secret 或宿主挂载的明文，会被处理它们的基础设施看到。

实现

Kubernetes 如何创建 PodVM

先看本地 Kata 运行时如何创建虚拟机，再看 Peer Pods 如何改变虚拟机的部署位置。

  1. 选择运行时。 Pod 的 runtimeClassName 引用 RuntimeClass，后者的 handler 指向节点 CRI 中已配置的运行时。
  2. 启动沙箱。 Kata shim 启动 VMM，Guest 随之引导。shim 通过 vsock 等传输转发生命周期 RPC，Guest 中的 Kata Agent 按策略检查宿主请求。
  3. 准备根文件系统。 在 containerd 架构中，Nydus 等 snapshotter 将镜像准备工作引导到 Guest。Kata Agent 调用 Confidential Data Hub（CDH）的镜像拉取 API。Guest 用 image-rs 获取并解包 OCI 镜像，用 ocicrypt-rs 处理加密层。

在 Peer Pods 模式中，Cloud API Adaptor（CAA）调用云平台 API，在 Worker 旁创建独立的 PodVM，并转发 Agent 流量。Worker 本身可以是虚拟机。机密保护取决于实例类型、Guest 镜像以及可验证的硬件证据。

TRUSTEE

从硬件报告到资源授权

Attestation Agent（AA）获取 TEE 证据。Trustee 代表工作负载所有者评估证据，CDH 在 Guest 内使用受保护的资源。

服务职责
Key Broker Service (KBS)管理证明交互，根据已验证的声明与资源路径作出发放决定。用已证明的 Guest 公钥保护返回的资源。
Attestation Service (AS)运行对应平台的验证器，检查证据及其绑定，按策略评估 TCB 声明。TDX Quote 与 SNP report 使用各自的背书和验证流程。
Reference Value Provider Service (RVPS)向 AS 提供预期度量等经批准的参考值。参考值的来源与更新流程属于可信部署的一部分。

证据绑定 KBS 的挑战值和 Guest 内生成的公钥。新鲜度检查阻止旧报告被用于新的挑战。公钥绑定让 KBS 能将响应加密给生成证据的 Guest，即使流量经由基础设施转发。

配置度量

三类策略如何协作

VM 启动度量标识初始 Guest 环境。工作负载镜像在后续加载。CoCo 可用 Init-Data 绑定该工作负载的配置，由已度量的 Guest 执行策略。

策略执行者决策示例
Kata Agent PolicyKata Agent只允许指定的容器镜像 digest 与挂载配置。若应用禁止宿主发起 exec，则拒绝 ExecProcessRequest。
Attestation Service PolicyTrustee AS检查平台 TCB 基线和预期的 Guest 度量。
KBS Resource PolicyTrustee KBS只有身份声明符合预期且资源路径匹配时，才发放支付服务的密钥。

Kata 的 genpolicy 可以根据工作负载清单生成 Agent 策略。审阅规则后，将策略与 Guest 配置打包为 Init-Data。按 CoCo 文档，启动时可把其摘要绑定到 TDX 的 MRCONFIGID 或 SNP 的 HOST_DATA。Guest 核对配置与绑定值，远端还需把该值或经验证的声明与所有者批准的配置比较。

Init-Data 是可经过控制面的完整性受保护配置。敏感材料通过 KBS 或 Sealed Secret 交付。

镜像与数据路径

加密 OCI 镜像如何变成运行中的容器

构建流水线加密镜像层，并将镜像发布到 OCI Registry。加密后的 OCI descriptor 可携带 key provider 元数据，匹配的密钥资源预先配置到 Trustee 或它使用的秘密后端。

Guest 拉取加密 blob，由 CDH 处理 key provider 路径。需要证明才能访问的密钥资源，由 KBS 在返回前执行资源策略。Guest 解密镜像层并准备容器根文件系统。Registry 和基础设施仍可能看到 manifest 及 descriptor 元数据。

控制措施要验证什么
镜像 digest 与签名固定预期 digest，并在 Guest 内通过签名策略核对发布者身份。验证实际部署的镜像制品。
OCI 镜像层加密确认加密层只能用预期的密钥资源解密，并检查被拒绝的 Guest 无法取到资源。
Sealed Secrets 与受保护存储Sealed Secret 可以引用 KBS 保存的秘密，也可封装密文，由获准的 Guest 取用相应密钥。可写卷需要独立评估加密、完整性与回滚防护。
动手实验

先启动 Pod，再验证密钥拒绝路径

在已安装 CoCo Helm chart、配置匹配 CRI 的 Kubernetes 实验集群里，从公开镜像和测试数据开始。开发运行时用普通 VM 验证生命周期。

apiVersion: v1
kind: Pod
metadata:
  name: coco-smoke
spec:
  runtimeClassName: kata-qemu-coco-dev
  restartPolicy: Never
  containers:
    - name: hello
      image: docker.io/library/busybox:1.36
      command: ["sh", "-c", "echo CoCo-sandbox-ready; sleep 300"]
kubectl get runtimeclass
kubectl apply -f coco-smoke.yaml
kubectl describe pod coco-smoke
kubectl logs coco-smoke
kubectl delete pod coco-smoke
  1. 确认沙箱启动。 将 YAML 保存为 coco-smoke.yaml。在日志中找 CoCo-sandbox-ready。失败时先检查 RuntimeClass、Pod 调度、shim 和 Guest 启动，再排查证明。
  2. 验证硬件证据。 在兼容的 TDX 或 SNP 节点选择已安装的硬件 handler，例如 kata-qemu-tdx 或 kata-qemu-snp。按 CoCo 指南配置 Trustee、参考值、Init-Data 和加密测试镜像，确认匹配的 Guest 只能取得获准的测试密钥并启动镜像。
  3. 每次只改一个条件。 启动新的 PodVM，使用摘要正确但未被 KBS 策略授权的另一份 Init-Data。确认硬件证据能被评估，但取钥被拒绝。再单独请求未获授权的资源路径，或测试度量不符合 AS 策略的 Guest。通过 Trustee 和 Guest 日志定位失败阶段。会话有效但资源策略拒绝时，KBS 应返回 HTTP 403。

要独立验证 Guest 侧边界，可部署拒绝 ExecProcessRequest 的策略，检查已通过 Kubernetes 授权的 exec 请求是否仍被 Kata Agent 拒绝。开发 Pod 的成功用于确认编排，硬件实验再验证证明和真实的资源发放策略。
