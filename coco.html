SECURITY MODEL

A sandboxed Pod and a confidential Pod

Container security can cover isolation, image provenance or protection from the infrastructure operator. CoCo addresses the third case by running the Pod in a confidential VM and verifying its initial state before granting access to secrets.

ModelIsolation boundaryWhat the workload relies on
Ordinary OCI containerNamespaces, cgroups and kernel security controlsThe workload shares the worker’s kernel. A privileged host can inspect its state.
Kata ContainersA VM per Pod sandbox with a separate guest kernelVM isolation separates workloads from the worker. The protections against a privileged host depend on the VM technology.
CoCo on a hardware TEEA confidential PodVM backed by a platform such as Intel TDX or AMD SEV-SNPHardware protects private guest state. The workload owner uses remote evidence and policy to authorize sensitive resources.

The workload depends on the CPU and firmware, guest OS, in-guest runtime, application and the trusted verification and release services. The host still controls scheduling and can interrupt the VM. Shared I/O, traffic metadata and application logs need their own controls. Plaintext in a Pod manifest, Kubernetes Secret or host-backed mount is already available to the infrastructure handling it.

IMPLEMENTATION

How Kubernetes creates a PodVM

Follow the local Kata runtime path, then compare where the VM is provisioned with Peer Pods.

  1. Select a runtime. The Pod’s runtimeClassName refers to a RuntimeClass. Its handler selects a runtime configured in the node’s CRI implementation.
  2. Boot the sandbox. The Kata shim starts the VMM and the guest boots. The shim forwards lifecycle calls over a transport such as vsock. The Kata Agent checks the applicable guest policy before acting on host requests.
  3. Prepare the root filesystem. In the containerd design, a snapshotter such as Nydus routes image preparation to the guest. The Kata Agent invokes the Confidential Data Hub (CDH) image pull API. The guest uses image-rs for OCI image retrieval and unpacking and ocicrypt-rs for encrypted layers.

With Peer Pods, Cloud API Adaptor (CAA) calls a provider API to create a separate PodVM beside the worker and forwards the agent traffic. The worker can itself be a VM. The actual confidentiality properties still depend on the selected instance, guest image and verifiable hardware evidence.

TRUSTEE

From a hardware report to a resource decision

The Attestation Agent (AA) obtains TEE evidence. Trustee evaluates it on behalf of the workload owner. The CDH consumes the resulting protected resource inside the guest.

ServiceResponsibility
Key Broker Service (KBS)Manages the attestation exchange. Uses the verified claims and requested resource path to make a release decision. Encrypts the resource response for the attested guest key.
Attestation Service (AS)Runs the platform verifier, checks evidence and its bindings, and appraises TCB claims against policy. A TDX Quote and an SNP report have different endorsement and verification procedures.
Reference Value Provider Service (RVPS)Supplies approved reference values to AS, such as expected measurements. Their provenance and update process belong to the trusted deployment.

The evidence binds the KBS challenge to the public key generated in the guest. Freshness prevents reuse of an old report for the new challenge. The key binding lets KBS encrypt the response to the guest that produced the evidence, even when the infrastructure relays the traffic.

MEASURED CONFIGURATION

Three policies and one evidence chain

The VM launch measurement identifies the initial guest environment. Workload images arrive later. CoCo can bind workload-specific configuration through Init-Data and enforce it in the measured guest.

PolicyEnforced byExample decision
Kata Agent PolicyKata AgentAllow only approved container image digests and mount settings. Deny ExecProcessRequest when the workload disallows host-initiated exec.
Attestation Service PolicyTrustee ASCheck a platform TCB baseline and expected guest measurements.
KBS Resource PolicyTrustee KBSRelease the payments service’s key only for the approved workload identity and resource path.

Kata’s genpolicy can generate an agent policy from workload manifests. Review the resulting rules, then package the policy and guest settings in Init-Data. In the documented CoCo configuration, the launch binds its digest to TDX MRCONFIGID or SNP HOST_DATA. The guest checks the configuration against the bound value. The remote side must still compare that value or its verified claims against the owner’s approved configuration.

Treat Init-Data as integrity-protected configuration that can pass through the control plane. Deliver sensitive material through the KBS or a sealed secret.

IMAGE AND DATA PATH

How encrypted OCI layers become a running container

A build pipeline encrypts layers and publishes the image to an OCI registry. The resulting OCI descriptors can carry key-provider metadata. The matching key resource is provisioned into Trustee or its configured secret backend.

The guest pulls the encrypted blobs, and CDH handles the key-provider path. When the required resource is gated by attestation, KBS evaluates the resource policy before returning it. The guest decrypts the layers and prepares the container root filesystem. Manifest and descriptor metadata can remain visible to the registry and infrastructure.

ControlWhat to verify
Image digest and signaturePin the expected digest and use guest-side signature policy to verify the publisher. Verify the artifact that is actually deployed.
OCI layer encryptionVerify that encrypted layers require the intended key resource and that rejected guests cannot retrieve it.
Sealed Secrets and protected storageA sealed secret can reference a broker-held secret or wrap ciphertext with key material available to an authorized guest. Evaluate writable volumes separately for encryption, integrity and rollback requirements.
HANDS-ON

Start a Pod, then test a denied key request

On a Kubernetes lab cluster with the CoCo Helm chart and the matching CRI configuration, start with a public image and dummy data. The development runtime exercises the lifecycle with a regular VM.

apiVersion: v1
kind: Pod
metadata:
  name: coco-smoke
spec:
  runtimeClassName: kata-qemu-coco-dev
  restartPolicy: Never
  containers:
    - name: hello
      image: docker.io/library/busybox:1.36
      command: ["sh", "-c", "echo CoCo-sandbox-ready; sleep 300"]
kubectl get runtimeclass
kubectl apply -f coco-smoke.yaml
kubectl describe pod coco-smoke
kubectl logs coco-smoke
kubectl delete pod coco-smoke
  1. Confirm sandbox creation. Save the YAML as coco-smoke.yaml. Look for CoCo-sandbox-ready. If it fails, inspect RuntimeClass, Pod scheduling, shim and guest boot before investigating attestation.
  2. Exercise hardware evidence. On a compatible TDX or SNP node, select the installed hardware handler, such as kata-qemu-tdx or kata-qemu-snp. Configure Trustee, accepted reference values, Init-Data and an encrypted test image using the linked CoCo guides. Confirm that a matching Guest can retrieve only its test key and start the image.
  3. Change one condition at a time. Start a new PodVM with a different but internally consistent Init-Data that KBS policy does not authorize. Check that evidence can be evaluated but the key request is denied. Then separately change an allowed resource path or test a Guest whose measurements fail AS policy. Inspect Trustee and guest logs. A valid session denied a resource by KBS policy should receive HTTP 403.

To test the guest-side boundary independently, apply a policy that denies ExecProcessRequest and check that an otherwise Kubernetes-authorized exec request is rejected by Kata Agent. A successful development Pod tests orchestration. The hardware test adds attestation and real release-policy checks.
